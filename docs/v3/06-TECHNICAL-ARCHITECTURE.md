## Proposed technical boundaries

Reuse verified Supabase Auth rather than inventing credentials. The installed Auth client exposes password-reset and user-update capabilities, but the application has not implemented password change, forgot-password recovery or verified email-change journeys. Later work must design trusted callback handling, configured redirect allowlists, expired/replayed-link behavior and provider-required verification/reauthentication, with tests. The current [route guard](../../src/proxy.ts) and [auth actions](../../src/features/auth/actions.ts) cannot be assumed to already support recovery callbacks. No unrelated security-passphrase challenge is needed. Logout/login with another account is enough initially; isolate and clear or rescope private client state on session changes.

Verified session/owner enforcement is foundational to every private slice. Completing the whole Account Settings UI, password-change/email-change forms or an appearance/preferences dashboard is not a prerequisite for useful core writing. Deliver those in independently reviewed slices without weakening existing login/logout, isolation or required session-expiry recovery.

Ordinary content access should use the verified user's session and RLS, with owner/parent checks near each read/mutation. Privileged credentials stay server-only and narrowly scoped. Client IDs, hidden menus and company-switcher selection are not authorization. Apply isolation to search, recovery buffers, reference metadata, review results and context as well as committed content. Avoid shared caches of private results.

Treat capture creation, draft save, capture move, staging, review/follow-up and recording as distinct operations. P1 requires retries of the same capture save to resolve to that capture. Destination save plus capture removal must behave as one reliable move: failure preserves the source, and retry resolves to the same destination. P2 fixes candidate meaning as membership reflecting the current saved draft. P3 fixes explicit Thought identity and optional rationale. Record the exact confirmed revision/context together with ending pending membership, or recover a single known result; concurrent changes require reconfirmation. T2/T3 now settle server persistence and draft-resident staging; the transaction mechanisms below are recommendations implementing those choices, not new product workflow/history.

Store external-reference metadata, not source binaries. No object storage, upload service, PDF host, scraper, vector database, collaboration service or background agent is required for the stated MVP. Opening a link must not become a backend fetch; avoid automatic link previews that would introduce fetching/privacy scope. Validate safe external URL handling and sanitize rendered author/AI text without creating new ingestion features.

Preserve complete inspectable committed contents while avoiding a permanent full copy on every keystroke. Server autosave, bounded local recovery and persistent bounded review are settled directions; their concrete limits below are recommendations. Never silently drop unsaved work to save storage. V2 limits are evidence, not approved V3 constants. Keep operational logs separate from private draft/review/context content.

P4/P8 require confirmed whole-Thought deletion to remove its versions/snapshots while ordinary version/snapshot edits and selective version deletion remain disallowed. Draft deletion safely removes active candidate membership without touching committed records; cancelling submission retains the draft. Reference deletion cannot change external sources or recorded text. Secure owner/parent checks and coherent cleanup are required, but archive/trash, permanent pre-commit lineage and event sourcing are not. Technical retry receipts must be bounded and must not expose deleted content as an unintended history product.

P5 requires one document/editor format with guidance-only mode changes; no conversion pipeline or three persistence systems. P7 requires Title/URL only and inserts their values plus selected notes without deleting the catalog source; safe URL validation is not automatic fetching/verification. P6 outgoing context includes personal text already in the draft, plus deliberately selected additional material and bounded discussion. Context Snapshot and unrelated private material are not automatically expanded into it. Each initial/follow-up/refresh request is explicit and accounted; snapshot changes mark earlier results stale without semantic guesswork.

For AI, preserve explicit invocation, bounded context/output, ownership before spending, validated contracts and honest uncertain usage. Count any separately approved repair in reservations/settlement; no automatic repair is recommended for MVP. Show reported tokens and versioned estimated costs separately from actual provider billing. Settled T6 requires warnings plus server-enforced reservation checks; these still do not guarantee an invoice ceiling. The actual model, prices/FX and capability/configuration must be verified before separately authorized provider evaluation, without copying historical examples or PNG figures.

Reuse the [current composer](../../src/features/thoughts/thought-composer.tsx) input/preservation lessons, not its company-required capture semantics. Use JSON string transport for authored content, not form serialization that can change line endings. The V2 draft tests explicitly recognize textarea CRLF transport normalization; V3 must preserve the editor's source string end-to-end, including whitespace, Unicode and trailing newline. Do not trim, prettify or round-trip through a Markdown AST on save/commit. Reject unsupported NUL/size violations with retained input; never silently truncate. Native browser editing may represent pasted line endings differently from the original clipboard/file; promise preservation of authored editor source, not an unimplemented file-import byte guarantee.

For readable committed content/optional preview, propose the focused `react-markdown` renderer, subject to later pinned-version/license/security review. Its [maintainer documentation](https://github.com/remarkjs/react-markdown) describes safe React rendering and CommonMark support; custom components/plugins can change its security. Disable raw HTML; do not add MDX, `rehype-raw`, arbitrary plugins, embeds or automatic images. Override links with a strict HTTP(S) policy, no credentials or executable/data schemes; external links use safe new-window attributes when applicable. Render image syntax as inert alt text/URL rather than fetching remote media. Keep source readable when preview fails. This dependency recommendation is not an installation.

The existing [Refine comparison](../../src/features/refinements/refine-comparison.tsx) shows two documents but computes no diff. Recommend a small reviewed text-diff dependency such as [jsdiff](https://github.com/kpdecker/jsdiff), using deterministic line changes with whitespace/case sensitivity and explicit old→new inputs. Compare raw immutable Markdown, not rendered HTML. Store no diff as canonical history; both responsive views consume the same change model. Desktop pairs old/new line groups, narrow screens list removed/added lines in order with `−`/`+`, headings, line numbers and readable wrapping. Mark final-newline changes. Bound computation in a worker for large changes; on complexity/time limit show both exact sources with an honest unavailable-diff state, never a fabricated empty diff. jsdiff documents abortable `timeout`/`maxEditLength` controls; package version, limits and Unicode cases still need validation. No AI explanation, whitespace normalization or mutation of historical sources (T7/P3/P4).

## Draft save and recovery protocol

Proposed persistence shapes are owned by [Domain and Provenance](04-DOMAIN-AND-PROVENANCE.md#proposed-persistence-model). This protocol satisfies T2/T4 and P2/P5; it stores only the current mutable document.

1. Opening an owned draft loads exact Markdown plus `content_revision`. Track a separate local `edit_generation`, last acknowledged server revision/text and any in-flight save payload. Guidance changes do not change the content revision. Actual content changes advance it; exact no-ops do not.
2. On input, retain local text immediately, mark dirty and mark older review context as differing immediately, even before a save. Write a bounded recovery envelope on the separate local timer below. Start one save after the server debounce; allow one in-flight content save per draft per tab and coalesce later edits. Explicit save, stage, review and recording preparation flush pending intended content and await its actual acknowledgement. Do not rely on page exit to complete a server save.
3. Send draft ID, stable operation identity, expected saved revision and the exact captured string. Within a short transaction lock the owned draft, validate parents, compare expected revision, and change content plus increment revision only if different. A stale expectation returns conflict even when the caller thinks its string is newer; no last-writer-wins. Return operation ID, persisted revision and content acknowledgement. Stage/withdraw do not advance `content_revision`.
4. An acknowledgement applies only to its own owner/company/draft/operation and captured edit generation. Update known server revision monotonically; never set current editor text from an older response. Show **Tersimpan** only if the current editor string matches the acknowledged persisted state and no newer edit/conflict remains. If more edits arrived, keep dirty and save those against the acknowledged revision. Local recovery is cleared only for the matching acknowledged content, never newer input.
5. On network failure, retain recovery and the same operation identity. Query status or retry that exact save payload. Resolve uncertainty before submitting coalesced later edits; a revision read alone must not be mistaken for confirmation that this operation succeeded. An expired operation is not silently resubmitted as new. Authentication failure pauses writes and requests reauthentication to the same owner.
6. On conflict, preserve the unsaved local string and fetch the latest owned server text separately. Show both with explicit **use server** or **keep my text after review**; the latter submits a new action against the freshly displayed revision. No automatic merge/overwrite. Discarding either recoverable copy is deliberate. A different tab's storage event is a recovery signal, never permission to replace the editor.
7. On reload, validate recovery envelope schema, owner/environment/company/draft, base revision and any pending operation. If buffer equals confirmed server content, acknowledge it. If it differs, offer recovery while preserving the server copy; do not auto-apply based on client timestamps. If the draft was permanently deleted, never recreate it by autosave: explain unavailable state and offer text copy for the verified same owner. Expired buffers are handled under the policy below.

Recovery keys include **V3 environment + user UUID + company/draft UUID + tab ID**; Home unsaved captures use an owner/environment temporary operation key without requiring a company. Per-tab slots prevent competing tabs from overwriting each other's only buffer. Values hold current unsaved text, base revision, local generation, pending payload/operation when needed, timestamp and schema version, not a log of edits. Server remains authoritative. RLS cannot protect browser storage; keys prevent accidental account display, not access by somebody controlling this browser. Clear app memory, private query caches and local recovery on deliberate logout; do not falsely confirm cleanup if storage access fails. Before clearing unsaved text, offer save/copy or deliberate discard; never show it after signing into another account. Session expiry locks private presentation and permits same-owner recovery after verification. No offline-sync or guaranteed browser durability claim.

Proposed save-state transitions:

| State                     | Entry / permitted next step                                                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Loading / clean           | Load only after owner verification; matching acknowledged content is clean. First edit immediately enters dirty.                                                                           |
| Dirty / saving            | Debounce or explicit flush submits a captured generation; editing remains enabled. Matching acknowledgement enters clean only if no newer edits remain, otherwise dirty.                   |
| Uncertain / failed        | Timeout/transport failure preserves pending operation and recovery. Resolve same operation by status/safe retry before a newer payload; validation failure keeps text for correction.      |
| Conflict                  | Expected revision rejected. Keep local/server copies; explicit resolution creates a new expected-revision action. Never auto-merge.                                                        |
| Auth paused / unavailable | Stop requests on expiry/deleted parent. Verify same owner before recovery; missing/deleted draft cannot be resurrected. Logout requires clear app-private state or honest cleanup failure. |

## Critical writes, replay and conflict boundaries

All operation names below are **proposed interfaces, not existing RPCs**. Use an authenticated Next server boundary, runtime validation, user-JWT reads, and a short PostgreSQL transaction for multi-record writes. Ordinary clients receive no raw write grants that bypass these invariants. Narrow definer RPCs derive `auth.uid()`, check every parent, qualify identifiers, use an empty search path and revoke default PUBLIC/anonymous EXECUTE in the same migration. Their bypass of RLS makes these checks mandatory. Technical accounting alone uses the narrow service-role client after user authorization.

Use `(user_id, operation_id)` uniqueness, operation kind, server-derived payload HMAC and result IDs/status. Reusing a key with different content/target/options fails. Serialize concurrent identical operations before applying effects, return the same committed result, and atomically store the receipt with transactional effects. Server-issued expiry tickets bound to owner/kind/UUID prevent replay after bounded receipt deletion; expired/unknown outcomes require reconciliation, not an automatic new operation. Row-level creation/commit keys can supplement receipts while the object exists. Deletion leaves no private text in receipts; if a result has since been deleted, return completed-but-unavailable without resurrecting it. This is a technical retry mechanism, not pre-commit history (P1–P4).

### Empty-Company deletion and locking

Use Company→content lock order everywhere, companies sorted by UUID for moves, then draft/capture, then Thought, then dependent session/receipt rows. Operations also taking the owner AI budget lock take it before Company locks consistently; do not acquire it after a content lock. Keep transactions short and handle deadlock/serialization aborts by safe same-key retry/revalidation, never partial writes.

`delete_empty_company` takes an owned Company `FOR UPDATE` lock and, in subsequent READ COMMITTED statements, checks **all** owner-content children: captures with that company, Explore notes, writing drafts (therefore staged items), Thoughts and versions, References and any newly approved content relation. Review sessions are covered by their required parent draft; no orphan session is permitted. Every path creating/associating a child takes a parent `FOR KEY SHARE` lock before insertion, with composite owner/company FKs as a second safeguard. If insertion commits first, deletion sees it; if deletion wins, waiting creation finds no parent and fails without losing local text. Foreign keys use immediate `ON DELETE RESTRICT` from Company, including nullable capture association: **no CASCADE or SET NULL for research children**. An index supports each existence check. PostgreSQL documents [row-lock conflicts](https://www.postgresql.org/docs/current/explicit-locking.html) and [referential actions](https://www.postgresql.org/docs/current/ddl-constraints.html); these support the recommendation, but the actual V3 SQL and race behavior still require local integration tests.

Schema review must enumerate every inbound Company FK and every callable deletion function, not just the new UI. Fresh V3 migrations must not expose legacy V2 `delete_company`, `archiveCompany`, direct Company DELETE, unsafe definer helpers or service endpoints. If legacy objects exist in an isolated test baseline, revoke/drop unsafe function signatures and replace cascading FKs before any V3 write path is enabled. ## Persistent review and outgoing-context boundary

Store one bounded session per explicit new review/refresh, with owned draft/company, mode, exact saved revision and Markdown snapshot, explicitly selected extra material values, contract/model provenance and bounded messages (T5/P6). The [domain outline](04-DOMAIN-AND-PROVENANCE.md#proposed-persistence-model) owns fields. Follow-ups append to that session with an expected session counter and one in-flight request per session; reject conflicting sends rather than silently reordering discussion. Opening/reopening or switching guidance/review panels is a read. Guidance-only switching does not stale unchanged text; choosing a different review mode does not relabel an old result.

Before an initial/current refresh request, flush intended draft edits, display selected snapshot and additions, and freeze the exact authorized values. Check selected Explore/Reference IDs and specific note fields under the same verified owner/company; detect selection changes between preview and snapshot creation rather than fetching newer undisclosed contents. Include no hidden Company short note, account preference prose, other draft, source URL contents or Context Snapshot. V2's generic context builder can include Company `short_note`; do not inherit that expansion. A Reference URL is metadata, not source evidence. Personal text already copied into the draft is included.

Results arriving after edits stay on their original session/revision and are visibly stale; unsaved local changes produce immediate differing-content feedback. Reverting local text to the acknowledged snapshot removes only the unsaved-difference indicator; a newer saved revision still makes the older review stale. No-op saves do not manufacture staleness. A response for another selected draft/mode is stored for that authorized session and never injected into the active editor/panel as its current review. Follow-up on an old session sends its stored snapshot plus disclosed bounded discussion, not the current draft; explicit refresh creates a new current-snapshot session. Revalidate session/draft existence on result persistence after network I/O; deletion prevents resurrection. Deleting an Explore/Reference source does not retroactively rewrite explicitly copied draft/review text; disclose that copy boundary, and draft deletion removes its stored review copies.

Recommended V3 output contract: bounded review points/questions with explicit uncertainty, not a replacement document or pass/fail verdict. Runtime schemas bound item counts/text and validate references against selected inputs. Reuse the gateway's untrusted-data separation and sanitized failures, replacing Refine contracts/context/role enums with reviewed V3 modes. Store output only in the review session; no prompts/responses in diagnostics or accounting metadata. Invalid output ends that explicit request safely. No automatic schema repair in the MVP recommendation; any later approved repair requires a deliberate action, a separate accounted operation and reviewed bounds (P6).

## AI budget, dispatch and reconciliation

V2 evidence is concrete: `reserve_ai_run` takes a per-owner advisory transaction lock, checks settings and configured ceilings, reserves capped input/output costs for attempts, and `start_ai_run_attempt` uses a unique attempt row. `finish_ai_run` releases unattempted/known excess and retains conservative UNKNOWN charges. Its windows are UTC and its role/model overrides, `THOUGHT` input references and optional automatic second format attempt do not implement V3 T4–T6. Adapt these components rather than copying them unchanged.

Proposed V3 sequence (P6/T6):

1. Verify user and explicitly selected snapshot/context through the user-JWT path; validate full serialized request size, contract and one active server model's capability/configuration. Fail before any provider call if rates, credentials, bounds, ownership or budget are unavailable. Revalidate current provider documentation/pricing before later paid evaluation; no specific provider/model is selected here.
2. Under the per-owner budget lock, load authoritative owned budget/settings; reserve a conservative upper bound for **all billable input/output categories** using snapshotted price/FX/config versions and configured caps. Do not accept client prices, owner IDs or arbitrary budget values. Account for concurrent reservations, not just settled usage. Budget edits use the same lock; reducing the budget below consumed/held amount refuses further calls rather than retroactively refunding them. An optional reviewed server ceiling may tighten the owner's budget.
3. Recommend calendar months in **Asia/Jakarta**, visibly labeled, with UTC start/end instants derived server-side and frozen on each run. This is a technical recommendation requiring review, not a settled timezone choice or a new timezone picker. Test boundary instants; do not inherit V2 UTC windows invisibly. Reject a not-yet-started reservation after its period ends and release only its provably unstarted hold; a new request in the new period needs another explicit action. A request started before the boundary settles against its original period.
4. Claim the attempt exactly once transactionally, persist STARTED, commit, then transmit with SDK automatic retries disabled. An uncertain claim acknowledgement must not transmit. A duplicate action/status lookup returns the known operation; it does not call again. Network I/O is outside the DB transaction. A crash between STARTED and actual send can leave an unresolved hold: this is safer than speculative duplicate spend.
5. Persist actual reported tokens/provider request ID and validated result, then settle idempotently. For complete known usage release only unused reserved capacity under the frozen rates. Partial/unknown usage, timeout, ambiguous transmission or failed accounting keeps a conservative hold and honest pending/unknown status. Invalid output may still cost money. A model/rate mismatch triggers an accounting alert and blocks further calls until reviewed, not a fake zero/refund.
6. An unstarted claim can be canceled/released only when server state proves no sender could have started it. STARTED/unknown holds are never refunded solely by age. Later authorized reconciliation may use reliable provider evidence/manual review; no provider inspection or paid retry is authorized now. Final result persistence checks whether the draft/session was deleted: discard private output if so, retain minimal usage/uncertainty, and never recreate content. Client timeout/disconnect cannot promise provider cancellation.

This provides conservative application enforcement, **not exactly-once provider execution or a mathematically guaranteed invoice cap**. Provider accounting semantics, reasoning/cached tokens, failed calls, rounding, model aliases, FX and changing prices need verified compatibility. If a credible upper bound cannot be established, refuse transmission. Show measured tokens when reported, estimated monetary amounts with rate version, and held/uncertain amounts separately from provider invoices. All initial reviews, follow-ups, explicit refreshes and separately approved repairs use the same boundary. Budget exhaustion leaves manual writing, saving, References and Thought recording functional. One server-configured active model serves all three modes; remove V2 per-role model routing from the V3 active path and add no Settings model picker.
