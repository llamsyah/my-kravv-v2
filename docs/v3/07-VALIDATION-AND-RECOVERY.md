## Recovery expectations

An autosave acknowledgement identifies the actual persisted numeric revision and captured text. T2 is settled: Supabase is primary, bounded local recovery is temporary protection, without a full offline/sync guarantee. Failure/delayed acknowledgement must not erase newer input or display Tersimpan for unacknowledged content. Conflicts preserve local and server strings for explicit resolution. T5 requires persistent bounded draft reviews. [Architecture](06-TECHNICAL-ARCHITECTURE.md#draft-save-and-recovery-protocol) owns transitions and recommended buffer/receipt limits; none requires permanent per-autosave history.

Capture moves must handle destination save/source removal as one coherent operation, including lost-response retries: one destination, no accidental capture loss, and the source preserved if the move fails. A simple technical operation receipt can resolve uncertainty; permanent capture lineage, archive/trash or event sourcing is not the product acceptance target.

Staging and commit use distinct operation identities and expected saved revisions. A candidate tracks the live draft, not a frozen submission. Batalkan Pengajuan retains the draft; restaging cannot create duplicate active membership. Save intended pending edits before review, verify the exact confirmed revision at record time, and reconfirm if it changes. Replaying a commit recovers its existing result, not another version. A lost response cannot leave both committed history and an actionable duplicate candidate; if uncertain, show honest bounded recovery. Do not add a second candidate editor/history or elaborate background reconciliation product.

Confirmed draft deletion must either remove its staging flag and review sessions coherently or preserve the existing state on failure; no orphaned action or committed-Thought cascade is allowed. Whole-Thought deletion securely removes all versions/inline snapshots together; failures cannot permit selective history deletion. An earlier Context Snapshot cannot be edited separately or normalized from hindsight. Test unknown/absent personal context honestly, not by generating replacement values. Settled C1 refuses Company deletion with any related content; V2 cascades are explicitly invalid V3 acceptance behavior.

Review responses arriving after a draft edit remain linked to the submitted snapshot and visibly stale. Test explicit continuation with that older context versus explicit refresh of the current draft, context selection changes, bounded discussion and per-follow-up reservations/usage. Personal text already copied into the draft is included and disclosed; unselected source/private notes and Context Snapshot are not secretly fetched. Unknown usage is not zero cost and does not trigger automatic paid replay. AI failures/budget exhaustion leave manual saving and recording usable.

Session expiry during editing requires safe reauthentication and recovery without exposing text to another account. Logout/login with a different owner must rescope in-memory state, local recovery keys, queries and cached/private content. Expired recovery/email-verification links must fail safely and must not authorize private routes merely because a browser has a token-looking value.

## Security and integrity evidence

Use deterministic tests with synthetic author text and injected provider/database boundaries for preservation, context selection, replay, staleness, pricing uncertainty and rendering. Retain the relevant V2 regression assertions, adapting only those whose semantics change through reviewed V3 contracts.

Later authorized database/integration testing should cover anonymous access, foreign IDs, malformed/missing IDs, ownership/parent mismatches, row-level policies, column/write permissions, atomic commit/queue transitions, unique operation identities, concurrency and deletion restrictions. UI hiding is not a substitute for these controls. Restrict privileged clients to reviewed administration/accounting paths; never expose credentials in client data, rendered errors or logs. Text/links supplied by the owner, sources or AI require safe rendering and safe URL handling.

Live tests require a designated development environment and explicit authorization, disposable synthetic records and verified cleanup. A mock provider does not prove deployed RLS or real-model semantic quality. Real-provider evaluations, if later approved, need a separately bounded request/cost plan; historical smoke-test authorization and this documentation task grant no provider allowance.

## UX and visual evidence

Evaluate [UX states](05-UX-AND-DESIGN-SYSTEM.md) in light and dark mode, with long/empty text, many companies/drafts/versions, narrow layouts, keyboard-only navigation, visible focus, zoom/reflow, screen-reader feedback, reduced motion and phone keyboard/safe-area conditions. Reading width remains controlled when either panel collapses. Diff changes must be understandable without color alone. Review and record can proceed without AI or optional personal context.

Static PNGs demonstrate none of these runtime behaviors. Avoid bulk screenshot matrices in curated reference folders: temporary captures/logs/measurement JSON belong in ignored `.qa/<task>/`; only deliberately selected documented evidence should be promoted.
