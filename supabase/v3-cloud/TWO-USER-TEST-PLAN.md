It then exclusively creates `run-<runId>.manifest.jsonl`. Auth request bodies, passwords, keys, emails, cookies, token bodies and raw server errors are never written. A sending event without a verified event means the mutation outcome is uncertain. Claim or manifest failure aborts; no network may proceed without that evidence. A disk failure can prevent a final failure event, so never infer completion from the absence of an error event. Every manifest event is encoded as one UTF-8 buffer; the returned write byte count must equal the full buffer length before fsync. Any short/zero write, write exception or fsync error fails closed. The runner freezes a manifest whose persistence failed instead of appending failure JSON to a potentially truncated tail. Intended-write records must be fully written and fsynced before transmission; verified-ID records must be fully written and fsynced before dependent requests. Retain the consumed claim and inspect incomplete tails conservatively; a complete-looking line alone is not durability proof. Never treat an existing claim as test success.

### Enforced API behavior and limits

The engine generates its own immutable-in-use request sequence from the validated grant; it accepts no arbitrary method/URL/body inputs. Every outbound request, including identity/login/logout, consumes the 48-request budget. A monotonic clock enforces the overall 180-second limit, with independent wall-clock grant-expiry checks. Each request and its response body have a maximum ten-second timeout capped by remaining run time. Abort signals and timeout races stop stalled bodies; responses over 256 KiB, invalid JSON, any redirect or changed response URL fail. There are no SDK refreshes or retries, and no SQL/admin/delete/signup endpoint. The timer cannot preempt a blocked OS filesystem call, but elapsed local preflight time is charged before any request and no network continues after expiry.

Before writes, exact marker, both confirmed users/UUIDs/emails, session JWT issuer/sub/role/expiry and all empty baselines must pass. JWT payload checking is defense in depth, not signature verification: the following authenticated Auth user request independently verifies the session at the exact service. RLS operations use only each user's token plus the publishable key; anonymous/identity checks have no user Authorization. Logout clears only the run's in-memory session; the following unauthenticated request omits that token. Immediate revocation of every prior JWT is not claimed.

The separate offline simulator accepts only canned response data, not callbacks/transports, and only test-created temporary roots named `kravv-v3-offline-*`.
